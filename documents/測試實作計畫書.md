# 電商訂單與庫存管理系統 — 測試實作計畫書 (Test Implementation Plan)

本計畫書旨在為「電商訂單與庫存管理系統」規劃一套完整的測試集，涵蓋後端單元測試、API 功能測試、前端 API 模擬與完整使用者故事的整合測試。本計畫特別強調**「測試數據的安全隔離與自動清理機制」**，確保在不破壞現有資料庫數據的前提下，安全地驗證系統的正確性。

---

## 🎯 測試核心目標

1. **後端程式測試**：驗證 Flask 後端邏輯、密碼雜湊、JWT 簽發與資料庫連線的正確性。
2. **前端 API 請求測試**：確保前端各視圖（Views）發送的請求與 API 契約相符，且能正確處理成功與失敗的回傳。
3. **使用者故事整合測試**：模擬真實世界的操作流程（從註冊到出貨），確保業務邏輯無漏洞。
4. **資料庫互動與事務（Transaction）驗證**：驗證行級鎖定（防超賣）、交易回滾（防局部寫入）以及觸發器（Trigger）的運作。
5. **資料庫防污染清理（Clean-up）**：測試結束後，自動將測試所產生的臨時資料（如測試會員、測試訂單、測試庫存日誌）徹底刪除，使資料庫恢復原狀。

---

## 🧹 測試資料清理機制 (Anti-Corruption & Clean-up)

為了防止測試資料殘留在 `ecommerce_db` 中導致資料庫污染或崩壞，我們將採用以下兩種清理策略：

### 策略 A：動態事務回滾 (DB Transaction Rollback) — 適用於唯讀與局部寫入測試
在 Python 測試腳本中，每次測試開始時開啟一個資料庫事務（Transaction），測試結束後強制調用 `conn.rollback()`，如此所有測試寫入都會自動消失，且完全不影響資料庫實體。

### 策略 B：特徵標記與主動清理 (Targeted Clean-up) — 適用於跨 API 的整合測試
由於許多 HTTP 請求在 Flask 中會各自建立連線並自動 Commit，無法單一回滾。因此我們採用**「特徵標記法」**：
1. **統一前綴**：所有測試產生的會員 Email 一律使用 `test_` 開頭（例如 `test_user_99@example.com`），測試商品名稱一律使用 `[測試專用]` 開頭。
2. **級聯刪除 (Cascade Delete)**：
   * 由於資料庫設計中建立了外鍵約束，我們可以利用 `DELETE FROM MEMBERS WHERE email LIKE 'test_%'`。
   * 會員刪除後，其關聯的 `ORDERS` 會因為外鍵限制被拒絕或刪除（在本系統中，`ORDER_DETAILS` 設定了 `ON DELETE CASCADE`，而 `ORDERS` 設定了 `ON DELETE RESTRICT`，因此清理時必須**逆向刪除**）。
3. **清理順序 (逆向約束)**：
   ```sql
   -- 1. 刪除測試訂單產生的庫存日誌
   DELETE FROM INVENTORY_LOGS WHERE product_id IN (SELECT product_id FROM PRODUCTS WHERE name LIKE '[測試專用]%');
   -- 2. 刪除測試訂單的明細
   DELETE FROM ORDER_DETAILS WHERE order_id IN (SELECT order_id FROM ORDERS WHERE member_id IN (SELECT member_id FROM MEMBERS WHERE email LIKE 'test_%'));
   -- 3. 刪除測試訂單主表
   DELETE FROM ORDERS WHERE member_id IN (SELECT member_id FROM MEMBERS WHERE email LIKE 'test_%');
   -- 4. 刪除測試會員
   DELETE FROM MEMBERS WHERE email LIKE 'test_%';
   -- 5. 刪除測試商品
   DELETE FROM PRODUCTS WHERE name LIKE '[測試專用]%';
   ```

## 📖 使用者故事與整合測試場景 (User Stories & Integration Scenarios)

本計畫書規劃了 4 大使用者故事來覆蓋系統的現實業務邏輯：

### 故事一：新會員的完整購物下單流程
* **角色**：一般顧客
* **現實邏輯**：一個新使用者來到網站，註冊帳號，挑選商品加入購物車，送出訂單並完成付款。
* **測試步驟**：
  1. 呼叫 `POST /api/auth/register` 註冊一個測試帳號 (`test_shopper@example.com`)。
  2. 呼叫 `POST /api/auth/login` 驗證登入並取得 JWT Token。
  3. 呼叫 `GET /api/products` 查詢商品列表，選取一個庫存充足的商品（記錄當前庫存 $S_1$）。
  4. 呼叫 `POST /api/orders` 建立訂單，購買該商品 2 件，提供收件電話與地址。
  5. 驗證資料庫：
     * `ORDERS` 表新增一筆訂單，付款狀態為 `未付款`。
     * `ORDER_DETAILS` 表新增一筆明細。
     * `PRODUCTS` 表中，該商品的庫存已自動扣減為 $S_1 - 2$。
     * `INVENTORY_LOGS` 自動新增一筆 `-2` 的 `訂單扣減` 記錄。
  6. 呼叫 `POST /api/orders/<id>/pay` 進行模擬付款。
  7. 驗證資料庫：訂單的 `payment_status` 更新為 `已付款`。

### 故事二：高併發搶購與防超賣測試 (Concurrency Control)
* **角色**：多位熱門商品搶購者
* **現實邏輯**：當熱門商品只剩 1 件時，兩位顧客同時按下購買，系統必須保證只有一人能成功，且庫存絕不能變成負數（$-1$）。
* **測試步驟**：
  1. 後端將測試商品的庫存設為 `1`。
  2. 使用多執行緒（Multi-threading）模擬兩個不同的測試會員，同時發送 `POST /api/orders` 下單請求。
  3. 驗證結果：
     * 只有一個請求收到 `201 Created` 成功回應。
     * 另一個請求收到 `400 Bad Request`，錯誤代碼為 `INSUFFICIENT_STOCK`（庫存不足）。
     * 資料庫商品庫存必須為 `0`，絕不可為負數（驗證 `CHECK (stock_quantity >= 0)` 約束與 `FOR UPDATE` 行級鎖定）。

### 故事三：管理端商品上架與顧客端同步
* **角色**：系統管理員與顧客
* **現實邏輯**：管理員在後端後台新增一個新商品，顧客重整前台網頁後能立即看到該商品，並且可以開始購買。
* **測試步驟**：
  1. 使用管理員帳密登入並取得 Token。
  2. 呼叫 `POST /api/admin/products` 新增一個 `[測試專用]極致登山杖`，價格 $1000$，初始庫存 $50$。
  3. 呼叫會員端 `GET /api/products`，驗證回傳的商品清單中已包含該商品。
  4. 模擬顧客下單購買 1 件該商品。
  5. 驗證管理員呼叫 `GET /api/admin/dashboard/stats` 時，今日訂單數與營業額已正確加計該筆金額。

### 故事四：訂單取消與退貨流程（庫存回滾驗證）
* **角色**：客服管理員與顧客
* **現實邏輯**：顧客下單後因故聯絡客服退貨，管理員在後台將訂單狀態更新為已取消，系統必須自動把扣減的庫存加回去。
* **測試步驟**：
  1. 顧客下單購買商品 3 件（庫存減少 3 件）。
  2. 管理員呼叫 `PATCH /api/admin/orders/<id>`，將該訂單的 `order_status` 修改為 `cancelled`。
  3. 驗證資料庫：
     * `ORDERS` 表中的狀態更新為取消。
     * `INVENTORY_LOGS` 自動被寫入一筆 `+3` 的 `取消退回` 紀錄。
     * `PRODUCTS` 表中，該商品的庫存已自動加回 3 件。

## 🛠️ 測試實作技術架構

### 1. 後端單元與功能測試 (Backend Tests)
* **工具**：Python 內建的 `unittest` 模組。
* **執行檔案位置**：`backend/tests/test_backend.py`
* **覆蓋範圍**：
  * 會員密碼雜湊與 `bcrypt` 驗證。
  * JWT Token 的簽發與解碼過期驗證。
  * 呼叫 API 登入、註冊的邊界條件（如密碼過短、Email 重複、必填欄位缺失）。

### 2. 前端 API 整合測試 (Frontend API Tests)
* **工具**：`pytest` 搭配 `requests` 庫，直接模擬前端發出的 HTTP 請求，驗證 API 端點。
* **執行檔案位置**：`backend/tests/test_frontend_api.py`
* **覆蓋範圍**：
  * 商品分類列表、搜尋、排序的 API 回傳格式與資料型態。
  * 會員在未帶 Token、Token 無效、或跨權限讀取他人訂單時，後端是否能正確回傳 `401 Unauthorized` 或 `403 Forbidden`。

## 📅 實作時程與驗證計畫

1. **第一階段：建立測試腳本目錄與基礎工具**
   * 建立 `backend/tests/` 資料夾，並撰寫 `db_cleaner.py` 輔助模組，實作測試資料的自動清除邏輯。
2. **第二階段：編寫後端與 API 測試集**
   * 撰寫 `test_backend.py` 驗證底層邏輯。
   * 撰寫 `test_frontend_api.py` 驗證路由與 API 契約。
3. **第三階段：編寫使用者故事整合測試**
   * 撰寫 `test_user_stories.py` 模擬高併發與完整交易流程。
4. **第四階段：配置一鍵測試批次檔**
   * 在專案根目錄建立 `run_tests.bat`，讓開發者或審查老師能一鍵啟動測試，並在測試完成後於終端機顯示：
     `[OK] 測試完成！已自動清理所有測試產生的暫存資料，資料庫無污染。`
